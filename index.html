How it works

Your tool returns a link, not a yes. The shopper's wallet decides.

When an agent calls a tool you've gated, the gate answers with what's required and an approve link. The shopper proves it on their phone, your server verifies it, and only then does the order complete.

  1. The shopper asks the agent: “Buy the Oak Whiskey.”
  2. The agent calls your checkout tool.
  3. Your server answers: needs age_over_21 + payment, and here's the approve link.
  4. The agent hands the link (or a QR) to the shopper.
  5. The shopper opens it and approves in their wallet.
  6. The wallet presents the credentials to your server (OpenID4VP).
  7. Your server verifies the proof and re-prices the order itself, then completes it.
  8. The agent sees the order settled and carries on.
The agent never holds a credentialIt carries a link. The proof travels wallet → your server.
Enforced on your serverAmount and policy are re-derived server-side; there's no button the agent can click past.
Works in any MCP clientClaude, ChatGPT, Goose — the tool just returns text and a link. No client plugin.

Get started

Gate your first tool in three steps.

For an MCP server you already run. Starting from nothing? The storefront gives you a whole gated store instead.

1

Install the gate

One package, types included. It has no MCP SDK dependency, so it fits whichever MCP server you already use.

npm i @openmobilehub/credentagent-gate
2

Wire the checkout once, at startup

orders.serve(app) adds the approve page and the wallet proof rails to your Express app.

import { CredentAgent, age, payment, required, } from "@openmobilehub/credentagent-gate"; const credentagent = new CredentAgent({ walletOrigin: "https://shop.example", // your public origin }); credentagent.orders.serve(app); // approve page + proof rails // fires once the shopper approves credentagent.on("order.settled", ({ id }) => fulfill(id));
3

Return an approve link from your checkout tool

Create the order with its policy and hand approveUrl back to the agent. A status tool reads orders.retrieve(id) — MCP has no push, so the agent polls it.

// inside your MCP checkout tool const { id, approveUrl } = await credentagent.orders.create({ order, // { id, total, currency, lines }, priced by your server policy: [required(age.over(21)), required(payment.in("usd"))], }); return { content: [{ type: "text", text: `Approve here: ${approveUrl}` }], }; // inside your order-status tool await credentagent.orders.retrieve(id); // → { ok: true, completion } or { ok: false, pending: true, approveUrl }

You'll need

  • Node 20+ and an Express-style app
  • Any MCP server — the gate brings no SDK of its own
  • A phone with Multipaz Wallet (Android & iOS) to approve gated orders

Before you go live

  • credentagent.doctor({ print: true }) flags an ephemeral GATE_SECRET, a localhost walletOrigin and in-memory stores.
  • Credential checks are presence-only-demo until issuer trust ships — see Status.

One policy line per rule your merchant needs.

Age, membership and payment are built in. Anything else a wallet can hold, you define.

Go further

Let the agent buy on its own — within limits the shopper signed.

When the checkout works, these are the next pieces merchants ask for: unattended purchases, your own catalog and order store, and a signal to fulfillment.

Approve once — with a signature. The human sets a bounded budget (how much, per purchase, and what), and the grant only becomes spendable after their phone wallet signs those exact limits. The agent then buys against it unattended, every rule re-checked server-side on every spend. Age is never delegated to the agent: a 21+ item needs the human's own proof — from their wallet while approving the grant, or live at checkout. Without it, the spend refuses.

credentagent.grants.serve(app); // serves each grant's signing page const grant = await credentagent.grants.create({ merchant: "utopia", budget: 200, perSpend: 130, allow: { categories: ["Beverages"] }, // bound WHAT may be bought, not just how much }); // signing defaults to "device" sendToUser(grant.approveUrl); // → the wallet signs the grant's exact bounds // later, human away const g = await credentagent.grants.retrieve(grant.id); g.trustLevel; // "device-signed" — real signature, demo trust anchor const s = await g.spend({ idempotencyKey: "order-1", items: [{ sku: "coffee" }] }); // → { ok: true, … } or { ok: false, code: "budget-exceeded" | "step-up" | … } await g.revoke(); // kill-switch — the very next spend refuses

Bring your own catalog and order store. Already have an Express + MCP server, a catalog, and an order store? defineHost() takes those three things and builds the rest — one completion choke point your own tools call, fail-closed on an incomplete setup.

const host = defineHost({ catalog: { createOrder: (items, id) => priceFromMyCatalog(items, id) }, // amount source of truth orderStore: { read: (id) => myOrders.get(id) ?? null }, records: { read: (id) => myCompleted.get(id), write: (rec) => myCompleted.set(rec.orderId, rec) }, signingKey: process.env.GATE_SECRET, }); host.publish(app); // publish the seams onto your app new CredentAgent({ walletOrigin }).mount(app); // serve the proof pages over them // your own place-order tool calls host.complete(…) → { completed, reason? }

Tell a different service when an order settles. A signed order.settled POST — HMAC-SHA256, replay-protected, retried at-least-once — verified on the other side with the familiar constructEvent idiom.

// sending — configure once new CredentAgent({ webhooks: { endpoints: [{ url: "https://fulfillment.example/hooks", secret: process.env.WHSEC }] } }); // receiving — a different service; verify the RAW body const event = constructEvent(req.body, req.get("CredentAgent-Signature"), process.env.WHSEC); if (event.type === "order.settled") fulfill(event.data.object.orderId); // dedupe on event.id

Gate on any credential a wallet can hold. defineCredential() takes a DCQL request, a claim check and the orders it applies to; it then sits in a policy next to the built-ins.

import { defineCredential, dcql, gate } from "@openmobilehub/credentagent-gate"; const prescription = defineCredential({ id: "prescription", request: dcql({ docType: "org.hl7.prescription.1", claims: ["rx_valid"] }), verify: (c) => c.rx_valid === true, effect: gate(), appliesTo: (order) => order.lines.some((l) => l.requiresRx), ui: { label: "Prescription", action: "Verify prescription" }, });
Status · honest by design

Pre-1.0. Here's exactly what's real, and what production still needs.

The site follows the SDK's own trust_level — it never claims more than the library enforces.

✓ Real today

  • Passkey approvals — real WebAuthn, origin-bound, replay-protected
  • Signed order.settled webhooks (HMAC-SHA256)
  • Wallet device signatures over a spending grant's exact limits
  • Server-side enforcement: amount and policy re-derived on completion

⚠ Demo-grade today

  • Wallet credentials (age, membership, payment) are presence-only-demo: the wire crypto is real, but with no issuer trust anchor a self-crafted credential would pass
  • Wallet-signed grants: real signature, demo trust anchor
  • Click-to-approve grants — for demos and CI only

→ Before production

  • Issuer-verified trust — mdoc issuer/device signatures (Multipaz): the next milestone
  • Or relay a real external verifier — the interface ships; no adapter yet
  • Your deployment: a real GATE_SECRET, public walletOrigin, shared stores — doctor() checks them

The wire crypto is real; the issuer trust anchor is not yet — a self-crafted credential would still pass. Wallet-signed grants go one step further (the signature is real), but without an anchor they are still a demo. A presence-only gate is never sold as a real safety control. Branding can restyle the consent pages, but never the honesty footer.

Don't take our word for it — check a credential yourself

What the wallet sends isn't a CredentAgent token. It's a standard ISO 18013-5 mdoc: issuer-signed claims, a signed list of their digests, and a signature from the phone's own key. Independent tools from the OpenWallet Foundation's Multipaz project open it.

1 · Look inside

Paste any mdoc DeviceResponse into Multipaz Tools' viewer: document type, every disclosed claim, validity dates, per-claim digests, the device key. It decodes in your browser — nothing is uploaded.

Coming in the next gate release: inspectPresentations: true puts an Inspect this presentation link on the consent page (PR #223).

2 · Check the signatures

Multipaz Tools' verifier asks your wallet for a credential itself, then runs the Multipaz SDK's checks: the issuer's signature, each claim's digest, the device signature, and the validity window.

3 · See who signed it

The demo credentials are signed by Utopia Demo IACA — a certificate authority generated for this demo, not a trusted issuer. Open its certificate in the X.509 viewer.

What this shows: the credentials are real, standard, and signed. What it doesn't: that the issuer deserves trust — the demo CA is ours, and the gate itself doesn't check the issuer signature yet (presence-only-demo, above).
