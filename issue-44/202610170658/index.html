#44 Tint the browser bar to match the page (theme-color)

ready for human review

Add two <meta name="theme-color"> tags to index.html's <head> so mobile/desktop browser toolbars match the page background: #F2F4F0 for prefers-color-scheme: light and #0E1220 for dark (the current --bg tokens). Add a guard test in tests/theme.test.mjs so the metas can't drift from the tokens. No visible page content changes.

What changed

Added two `<meta name="theme-color">` tags to the `<head>` of index.html, so mobile and some desktop browsers tint their toolbar to match the page background. The light one (`media="(prefers-color-scheme: light)"`) is #F2F4F0 and the dark one is #0E1220. Both are the current `--bg` values from the two token blocks. Added a test in tests/theme.test.mjs that reads `--bg` from both token blocks using the existing LIGHT()/DARK() helpers, so no hex values are hardcoded in the test. It checks that the `<head>` has exactly one theme-color meta per colour scheme and that each one's colour matches its theme's `--bg` (case-insensitive). I wrote the test first and saw it fail on main because the metas were missing. I also changed the dark `--bg` on purpose and saw it fail with "dark theme-color must equal --bg", then put the value back. Nothing else on the page changed: no CSS, copy or script edits. Full suite: 87 passed, 0 failed. The self-contained grep prints 0. The issue's note about checking that the publish step can open a PR with AGENT_GH_TOKEN is about the pipeline, not a site change, so I made no change for it. I didn't touch .github/.

Limits: - **The toolbar strip is simulated.** Headless Chromium has no browser toolbar, so the top strip is an injected div painted with the matching meta's colour. It is not a real mobile browser bar. The real evidence is the DOM readout in the overlay. - **Possible mismatch in the fix itself (from reading the code).** The page picks its theme from localStorage, not from prefers-color-scheme: the boot script in index.html defaults to light. So someone whose OS is in dark mode but who never toggled the site's theme sees the light page (#F2F4F0) under a dark #0E1220 bar. The reverse also happens: OS light, site toggled to dark. The fix does what the issue asked for, and the captures only cover the matching cases. A maintainer may want a follow-up that updates the meta when the theme toggles. - **Test failures not shown.** The evidence plan also asked to show the new test failing on main and when --bg is changed or a meta is removed.
